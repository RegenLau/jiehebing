# 后台前端业务基线与接口交接清单

> 日期：2026-09-14
> 用途：作为技术团队替换 Mock 数据、接入真实服务端接口时的业务基线。
> 范围：管理后台前端、患者端相关联动、Node Mock 业务契约。PHP 服务端代码未修改。

## 一、必须保持的核心业务规则

### 1. 用药方案按版本生效

- 每次确认或调整生成新版本，不覆盖旧版本。
- 当天调整只替换调整时间之后尚未执行的服药计划；已完成、明确未服及调整时间之前的记录永久保留。
- 未来日期方案保存为“待生效”，当前方案在生效日前继续作为当前方案，疗程进度不提前重算。
- 普通调整沿用原疗程结束日期。只有显式提交 `adjust_course_end=true` 和新的 `course_end_date` 时才能延长或缩短疗程。
- 同一天重复保存方案不能重复生成已过时间点，也不能恢复已被替换版本的计划。

### 2. 分组配置采用入组快照

- 患者入组时保存分组的用药、问卷、任务、提醒和取药配置快照。
- 后续编辑分组配置只作为新患者默认安排，不直接影响已经入组的患者。
- 已入组患者后续生成任务、问卷轮次和取药提醒时读取患者快照或当前用药版本快照。
- 对某位患者确需调整时，通过患者研究管理生成个人方案版本，不回写分组模板。

### 3. 患者研究状态

- 状态值：`待启用`、`治疗中`、`暂停用药`、`已完成`、`提前退出`、`失访`。
- 患者完成身份确认、确认当前生效用药方案且治疗已开始后，自动进入`治疗中`。
- 所有有效方案均结束后自动进入`已完成`。
- 人工状态流转只允许：
  - `治疗中 → 暂停用药 / 提前退出 / 失访`
  - `暂停用药 → 治疗中 / 提前退出 / 失访`
  - `待启用 → 提前退出 / 失访`
- 暂停时只暂停当天起尚未执行的用药计划；恢复时只恢复当前或待生效方案的记录，旧版本记录不恢复。
- 提前退出或失访后取消普通未完成用药和随访任务。只有显式标记 `safety_followup=true` 的安全随访任务可以继续保留。

### 4. 问卷按任务轮次记录

- 每个问卷任务轮次都有独立 `task_id` 和 `answer_id`。
- 同一患者可以多次提交同一模板，但同一个任务轮次只能提交一次。
- 患者详情按轮次展示计划开放日期、最晚提交日期、状态和提交时间。
- 查看答案和导出必须按 `answer_id` 读取该次真实答案，不能按“患者 + 模板”返回第一份答案。
- 导出一行代表一次提交，必须包含患者编号、问卷轮次任务 ID 和提交时间。

### 5. 工作台指标与跳转范围一致

- “今日/近 7 天/近 30 天新增上报”按事件发生日期统计。
- “待跟进事件”统计截止所选日期仍未处理的全部事件，不受新增事件时间窗口限制。
- 待办跳转必须携带研究、分组、状态、逾期范围和统计截止日期，列表结果数应能与卡片数字核对。
- 图表首次进入页面即初始化，不能依赖切换日期或窗口尺寸变化后才显示。

### 6. 报告核对保留原始证据

- `ocr_result` 保存 OCR 原始识别结果，人工核对不能覆盖它。
- `reviewed_data` 保存正式人工核对值，包括报告类型、检查日期、文字结论、检验项目、核对人和核对时间。
- 核对人员可以纠正基础字段、文字结论和检验项目，也可以删除误识别检验项目或补录缺失项目。
- 影像、CT 等没有数值项目的报告允许只核对文字所见和结论。
- “需补充”只要求核对说明和明确的 `supplement_requirements`，不能强迫填写错误 OCR 指标。
- 导出必须分别输出“OCR 原始识别值”和“人工核对值”；未人工核对的数据不能标记为已核对。

### 7. 发药记录可追溯且防重复

- 建档、首次方案、首次发药组成一笔原子事务；任何一步失败时整笔回滚。
- 整笔建档和单次发药都支持 `client_request_id` 幂等键；相同键重试返回同一结果，不重复建档或发药。
- 发药错误通过“更正”或“冲销”处理，原记录永久保留并标记`已冲销`。
- 更正生成新的有效发药记录，并通过 `corrects_id`、`replacement_id` 关联原记录。
- 冲销记录不再计入余药和取药提醒计算。

### 8. 列表、筛选和导出

- 患者相关列表优先显示“姓名 + 患者编号”，手机号作为辅助信息。
- 患者、用药、随访、报告、不良反应和反馈支持按稳定患者编号检索。
- 用药导出必须完整沿用页面的状态、今日/全部、指定日期、逾期、逾期窗口、统计截止日期、研究和分组条件。
- 不良反应导出必须完整沿用严重程度、处理状态、负责人、待处理、统计截止日期、研究和分组条件。
- 不良反应导出同时包含上报状态、处理状态、负责人、最后处理时间和最后联系结果。

## 二、技术接入时需要实现的接口契约

| 接口 | 关键请求字段 | 必须保证的行为 |
| --- | --- | --- |
| `POST /app/core/patient/onboard` | `client_request_id`、`patient`、`treatment`、`dispense` | 原子提交；相同幂等键返回同一患者、方案和发药记录 |
| `POST /app/core/patient/treatment` | `user_id`、`start_date`、`adjusted`、`drugs`、`adjust_course_end`、`course_end_date`、`reason` | 生成版本；区分当前与待生效方案；保留历史事实 |
| `GET /app/core/patient/management` | `user_id` | 返回 `current_treatment_id`、`upcoming_treatment_id`、带 `version_state` 的历史版本、发药记录和操作历史 |
| `POST /app/core/patient/state` | `user_id`、`state`、`effective_date`、`reason` | 校验状态机；同步暂停、恢复或取消对应计划 |
| `POST /app/core/patient/dispense` | `client_request_id`、`treatment_id`、`issued_date`、`items`、`reason` | 幂等保存实际发药 |
| `POST /app/core/patient/dispense-correct` | `id`、`action=correct/void`、`client_request_id`、`reason`，更正时另带日期和明细 | 保留原记录；更正生成替代记录；冲销后不计入库存 |
| `GET /app/core/patient/survey-status` | `user_id` | 返回每个任务轮次的 `task_id`、`answer_id`、`round_no`、计划/截止日期和状态 |
| `GET /app/core/patient/survey-answer-detail` | `answer_id`，可同时带 `user_id` 做归属校验 | 精确返回该次提交，不按模板回退到其他轮次 |
| `GET /app/core/dashboard/overview` | `range`、`date`、`project_id`、`group_id` | 指标口径与列表筛选一致 |
| `GET /app/core/adverse-reaction/index` | `pending`、`as_of`、`processing_status`、`owner_id`、研究/分组 | `pending=1` 时返回截止日期仍未处理的记录 |
| `POST /app/core/report/review` | `status`、`reason`；通过时带核对后的类型、日期、`findings`、`metrics`；退回时带 `supplement_requirements` | 原始 OCR 与人工核对值分开保存，记录核对人和时间 |
| `GET /app/core/research/export` | `kind` 及对应页面全部筛选条件 | 导出完整筛选结果，不受当前分页影响 |

所有写接口都应保留操作人、操作时间、变更原因和前后值。多人同时编辑的对象继续使用现有 `revision` 规则做并发校验。

## 三、已调整的页面行为

- 用药计划首屏显示患者、编号、药品、剂量、应服日期/时间、状态和跟进操作，次要字段后置。
- 不良反应首屏突出严重程度、处理状态、负责人、发生时间和主要症状，并增加处理状态、负责人、研究和分组筛选。
- 报告核对页提供固定操作区、舍弃未保存修改、基础字段和文字结论编辑、指标新增/删除及明确的补充要求。
- 患者详情问卷区改为多轮列表，并可打开指定轮次答案。
- 随访任务增加任务详情和患者、关联报告、指定答卷跳转，来源统一显示为业务文案。
- 分组任务配置显示未来三次日期预览，并提供固定保存区和未保存提示。
- 新患者建档前两步增加字段级错误提示。
- 用药方案列表增加药品数、治疗天数、更新时间和只读方案预览。
- 日期字段按业务对象明确为入组日期、计划日期、检查日期、反馈日期或任务计划日期。

## 四、验收门槛

- Node Mock 全量业务测试必须全部通过，重点覆盖方案版本、分组快照、状态流转、多轮问卷、报告核对、发药幂等与冲销、工作台跳转和导出筛选一致性。
- 前端必须同时通过 Vite 构建和 `vue-tsc --noEmit`。
- 接入真实接口后，应使用同一组业务场景重新跑接口与页面验收；仅替换 URL 而未实现上述状态、快照、版本、幂等和筛选规则，不视为完成接入。
