# 后台全面评审与开发交接建议

评审日期：2026-09-14；代码基线：`abf46ba`。对象：当前 Vue 管理端、Node Mock、保留的 PHP 后端及现有交付文档。

## 结论与交付定位

**可以交给技术启动开发，但应命名为“前端交互与 Mock 业务规则参考基线”，目前不宜作为功能规则已冻结、仅替换数据即可上线的版本。** 页面主体和功能分区已经成形，不需要整体重做；主要差距是方案与任务的版本规则、患者状态、问卷轮次、待办/导出一致性，以及真实后台契约。

如果本周必须交接，可把当前代码与本报告一起交给技术，在任务单中明确待修和待决项；不要让技术把当前 Mock 的每一个返回结果都当作最终业务要求。正式冻结基线前，优先关闭 B01—B09、B16；真实服务联调前落实 T01—T07。

本轮仅评审，未修改业务源码，未启用原 PHP 服务、数据库或外部 OCR/微信服务。浏览器使用当前运行的本地 Mock，保留其现有演示数据；写入场景使用已有自动测试和独立内存夹具核对，没有通过页面保存患者、方案、报告或事件。

### 如何理解优先级和证据

- **P1：** 影响执行、数据真实性、核心操作或交接规则，应在对应模块开发/验收前解决。
- **P2：** 影响日常操作效率、理解或异常恢复，在第一版联调中处理。
- **P3：** 可后续优化，不阻塞第一版。
- **页面实证：** 本轮实际页面及保存截图；**逻辑复现：** 执行当前函数或隔离测试；**代码实证：** 完整相关分支阅读；**待定规则：** 需要产品明确的取舍，不伪装成已确认缺陷。

本报告不评判临床方案和药品剂量的医学正确性，不构成生产安全、法规或可访问性合规认证。

## 已有基础值得保留

1. 研究—分组—患者—个人方案—实际发药的主线清楚；三步建档降低跳页成本。
2. 通用方案、分组配置、个人调整有分层意图，部分接口已有快照和版本冲突检查。
3. 个人管理把基本信息折叠为摘要，发药、余药、状态和操作记录分开，符合业务使用习惯。
4. 报告原文件与结构化内容并排，保留上传及核对历史；界面如实标明 Mock OCR。
5. 不良反应处理表单已简化为负责人、处理状态、联系渠道和联系结果，适合作为首版人工跟进入口，不建议再扩成复杂评估大表。
6. 有统一 HTTP 封装、真实 XLSX 输出、文件上传、Mock 接口测试和可运行演示环境，技术可以在此基础上渐进接入。

## 功能逻辑：冻结基线前优先处理

### B01 · P1 · 同日改方案可能产生重复待服记录

**证据：逻辑复现。** `mock-api/followup.mjs:182`、`:213`；`mock-api/patient-management.mjs:36`、`:51`。

患者今日 08:00 已服药，10:00 保存今天生效的新方案，即使药品和时点不变，旧已服记录保留，同时生成新的 08:00 待打卡记录。隔离运行实际 `generateExecution` 得到同一日期时点一条 `status:1` 和一条 `status:0`。

**影响：** 再次提示患者记录已经服过的药；完成率、计划数和余药计算可能重复。

**调整：** 将“治疗原始起点”和“本次调整生效时间”分开，按版本及生效时点只重建未来未执行计划；保留已执行事实。保存前展示旧/新剂量、时点、影响日期。

**验收：** 当天已执行时点只有一条有效执行事实；同日反复调整、保存相同方案和超时重试不新增重复待服项。

### B02 · P1 · 未来方案立即被当作当前方案，疗程可能重新起算

**证据：逻辑复现＋代码实证。** `mock-api/patient-tasks.mjs:4`；`patient-app.mjs:81`；`patient-management.mjs:51`；`frontend/src/views/admin/patient/modules/management.vue:615`。

正在治疗时保存下周开始的新方案，当前逻辑直接选最后保存的一条。确认未来方案后患者启动阶段可能变为 `pending_start`，今天仍有效的旧方案入口被挡住；发药也默认关联最后一条方案。管理页载入旧方案时，又把 `start_date` 改成今天，沿用原治疗天数，服务端按新起点重算结束日。

**影响：** 提前切换方案、影响当前服药和发药；只改服药时间也可能把剩余疗程变成重新开始完整疗程。

**调整：** 区分当前、待生效、历史方案；按生效区间选择当前版本。明确总疗程结束日是否保持不变，延长疗程应作为明确操作。

**验收：** 未来版本生效前原方案可正常执行；改提醒时间不自动延长疗程；发药明确对应哪个方案；取消未来版本不影响既往记录。

### B03 · P1 · 分组任务配置会静默改变已入组患者

**证据：逻辑复现。** `mock-api/patient-tasks.mjs:42`；`pickup-reminder.mjs:14`。对照功能架构文档第 74—75 行关于入组副本、不覆盖旧患者的约定。

患者已有个人方案后，向其分组新增今天执行的检查任务，未调整个人安排，患者任务立即出现这条检查；取药提前天数也优先读取最新分组配置。

**影响：** 用药采用个人快照，部分任务与取药规则却随分组实时变化，版本原则不一致。

**调整：** 随访问卷、其他任务和取药规则都应明确个人快照。确实需要批量应用新规则时，显式选择患者范围和生效日，并记录变更。

**验收：** 只改分组默认值时旧患者安排不变；新患者采用新版；应用个人变更后仅改变未来安排，不改历史任务/答卷归属。

### B04 · P1 · 患者研究状态缺少正常流转

**证据：代码实证。** `mock-api/patient-management.mjs:25`、`:98`；`patient-app.mjs:1114`；`frontend/src/views/admin/patient/modules/management.vue:557`；`mock-api/server.mjs:552`。

新增患者固定“待启用”；完成身份、用药确认并不会更新该字段；当前管理页状态操作只有“提前退出”。统计又按 `study_state` 直接计算治疗中和已完成。

**影响：** 正常开始治疗的患者可能长期显示待启用，列表和统计失真。当前演示中还可见“已完成＋待确认方案”等组合，不能只靠几种颜色解释状态。

**调整：** 分别定义登录资格、是否登录过、身份确认、方案确认和研究状态。明确“待启用→治疗中→已完成”的条件；不把患者登录过等同于正在治疗或现在在线。项目结束时不再将无法执行的确认展示成待办。

**验收：** 建档→双确认→生效→结束全链路状态可解释，列表、详情、任务与统计一致，不需技术人员手工调 API 修状态。

### B05 · P1 · 多轮问卷导出重复首轮答案

**证据：逻辑复现。** `mock-api/server.mjs:168`、`:965`、`:979`。

导出遍历每份答卷，但解析答案时按患者 ID＋模板 ID 查第一份答卷。隔离验证同人 9/1 答“有症状”、9/8 答“已恢复”，导出两行时间正确，答案却都为“有症状”。表头还取首份历史快照，不同版本题目可能错列。

**调整：** 按答卷 ID 或任务轮次读取具体提交快照；导出带答卷 ID、患者编号、任务/轮次、模板版本。跨版本用稳定题目标识或分工作表。

**验收：** 同人三轮不同答案、仅筛第二轮、模板增加/停用题目后，详情与 Excel 逐题一致。

### B06 · P1 · 患者详情仍用旧的单次问卷规则

**证据：页面实证＋代码实证。** 截图 06、24；`mock-api/server.mjs:438`；`frontend/src/views/admin/patient-detail/index.vue:151`。

当前详情按“所有启用模板＋建档后开放天数＋首份答案”展示，不按分组安排和任务轮次。实际页面中，何雨晴所在分组配置为入组当天首次执行、每 14 天执行；患者详情却显示建档后第 7 天、可填写日 2026-08-31。页面没有逐轮答卷详情入口。

**调整：** 改成问卷任务/轮次列表，显示计划日、截止日、提交日、状态，点击看该轮答案；模板停用后保留历史记录。

**验收：** 第二轮未完成不会因第一轮已答而显示已完成；只显示该患者实际安排；历史答卷不会随模板停用消失。

### B07 · P1 · 工作台待办数与处理列表口径不一致

**证据：代码实证＋隔离逻辑验证。** `mock-api/server.mjs:624`；`frontend/src/views/dashboard/console/index.vue:249`、`:257`。

“待跟进事件”直接取统计日期内所有上报数，已处理的仍算待办，昨日未处理的可能不计入今日待办。事件/报告卡片跳转不携带项目、分组和待处理状态；事件列表接口本身也缺研究范围过滤。

**调整：** 趋势按日期范围统计；待办按当前研究范围＋未关闭状态累计。统一卡片、列表、导出使用的筛选条件；页面显示所处范围。

**验收：** 昨日遗留未处理事件今天仍可见；处理一件后计数减一；点击卡片后列表总数等于卡片，不能跳成所有研究全部状态。

### B08 · P1 · 图表首次进入可空白，切换范围后才恢复

**证据：页面实证＋代码实证。** 截图 01、23。本轮首次进入时三块图表持续空白，而数字已显示 30 位患者、62 条计划；切换近 7 天后三图正常绘制，浏览器未记录对应脚本异常。

`frontend/src/hooks/core/useChart.ts:390` 的可见回调创建图表后只发出 `chartVisible`，随即清除待绘制 options，没有应用配置；工作台直接使用基础 Hook，没有上层组件的事件处理。

**调整：** 基础 Hook 的延迟可见分支完成实际绘制；零数据、加载失败和正在加载分别提供状态。

**验收：** 首次访问、标签重新激活、滚动入视口、尺寸变化及日期切换均可绘制，不要求用户先点一次筛选。

### B09 · P1 · 报告核对缺少完整纠错路径

**证据：页面实证＋代码实证＋隔离逻辑复现。** 截图 16；`frontend/src/views/admin/reports/detail/index.vue:145`、`:184`、`:415`；`mock-api/reports.mjs:177`。

检验项目可以新增、编辑，不能删除误识别项。误点新增后留下空行，即使填写“要求补充”原因，也会被完整指标校验拦截。报告基础字段、CT 等文字结论只读，缺人工纠正入口。

**调整：** 允许删除误识别项、舍弃未保存修改；退回补充以原因和需补项目为条件，不要求先填完错误 OCR。明确可纠正字段与原始识别值、核对值的关系。影像报告按文字结论组织，不应统一提示补检验数值。

**验收：** 多识别、漏识别、错识别、空行、CT 结论错误、OCR 失败都能完成核对或退回，不需编造值绕过；修改有操作人、时间和版本。

### B16 · P1 · 用药页面导出会超出当前日期/逾期筛选范围

**证据：代码实证＋隔离逻辑复现。** `frontend/src/views/admin/medication-plan/index.vue:55`；`mock-api/research-export.mjs:204`；列表过滤见 `mock-api/server.mjs:480`。

今日用药列表限制当天，导出却没有传递或处理 `scope / plan_date / overdue / overdue_range / as_of`。隔离调用实际导出模块，在提供昨日、今日、明日三条计划、使用今日页实际参数时，三天全部导出。指定单日、历史逾期待办也存在扩大范围的风险。

**调整：** 列表与导出共用筛选参数和查询规则，处理 `status=0` 等不能用真值判断的枚举；统一日期边界。

**验收：** 今日、指定单日、近 7 天逾期、历史 as_of，叠加项目/分组和状态后，导出 ID 集合等于当前筛选列表全部分页的 ID 集合。

## 真实后台接入：需要实现的工作，不只是换数据

### T01 · 建立新版接口和现有 PHP 差异清单

当前 PHP `backend/config/route.php:113-153` 主要是旧版患者查询、用药列表和基础内容，没有覆盖新版项目/分组、连续建档、个人方案、发药、任务、报告、反馈等核心接口。旧动态菜单也不能直接提供所有新版入口。

同路径也需核对：前端患者查询有 keyword、study_state、project_id、group_id 和日期筛选，旧 `PatientController.php:16` 只读取分页，`PatientService.php:15` 返回旧字段。HTTP 200 不能作为接通标准。

**交付物：** 页面—接口—业务服务—数据表—开发状态矩阵，标注“可复用/需改造/需新增”；所有列表、详情、写入、导出逐字段对齐。

### T02 · 形成可直接实现的接口合同

现有 `docs/PROJECT.md` 适合导航，但缺复杂写入的字段约束、完整枚举、请求响应示例、空值和错误码。还存在 `research-export` 与实际 `research/export` 路径不一致，事件处理列旧 assess/contact 等文档漂移。

**至少明确：** ID 含义，必填/可空，数字单位与精度，日期/时区和当天边界，分页/排序，状态枚举，版本号，上传返回，导出筛选，错误格式。优先为建档、方案变更、发药、打卡、问卷提交、报告核对写示例和验收；可采用 OpenAPI 或等效结构化合同。

### T03 · 明确权限，不把负责人员当作已实现的数据隔离

Mock `server.mjs:140-145` 对所有账号返回 `R_ADMIN`、`*`；PHP 也主要为全权管理员。患者 `owner_id` 目前记录负责人，并没有形成列表/详情/导出/附件访问范围。

**产品先定：** 首版是否允许所有研究人员查看和修改所有研究数据；哪些人可管理账号、导出、调整用药、结束研究。可以采用简单权限模型，但必须明确。真实服务用不同范围账号验证查询、写入、导出和文件权限，不能只隐藏按钮。

### T04 · 用真实事务、版本控制和幂等保证数据可靠性

Mock 建档以 `structuredClone` 回滚，发药直接追加记录，患者 revision 有路径可省略，无法代表数据库并发行为。见 `patient-management.mjs:17`、`:55`、`:62-73`。

真实服务应保证建档相关对象原子保存；方案、任务、发药、打卡、报告提交有唯一约束或幂等键；核心编辑必须处理过期版本。

**验收：** 提交成功但响应超时后重试不重复；两人编辑得到明确冲突；任一步失败无半成品；重启服务数据和历史仍在。

### T05 · 定义附件、OCR 和提醒的真实状态

报告目前只接受本地 `/api/mock-files/`，附件从内存读取；文件路由在登录鉴权前返回资源。Mock OCR 同步完成，不能代表生产异步识别。原服务文件实现返回固定 OSS 地址，也不自动证明满足私有报告访问需求。

采用稳定 file_id，关联患者/报告，访问时校验权限或生成短期签名；OCR 至少有等待、解析中、成功、失败、重试/人工录入。保存原文件、原始识别值与核对后值。

提醒配置不等于消息已经发送。后端还需定义任务生成、待发送、发送成功/失败、重试与取消条件；同一患者同一轮提醒不能重复发送。微信资格、订阅状态或发送失败需有可查询结果。首版若仅保存配置，交接范围应明确标为未接真实发送。

### T06 · 原 PHP 登录安全行为需要追平新版约定

静态核对发现 `LoginService.php:35-42` 仅 uuid 非空才校验验证码；`AdminController.php:75-91` 改密/停用没有撤销旧 token，`AdminAuthMiddleware.php:20-32` 读取 token 快照，可能继续有效至到期。本轮未运行真实服务验证。

**验收：** 停用/改密后旧 token 下一次请求失效；缺验证码参数拒绝；退出后 token 不可复用。沿用 Mock 的会话隔离，不把其测试成功视为 PHP 已通过。

### T07 · 独立真实环境构建和联调验收

`frontend/package.json` 的 dev/build/serve 默认 `--mode mock`；Vite 的本地代理指向 3010，仅开发/预览有效。交接需保留 Mock 并提供独立真实联调/生产配置与部署反向代理说明，不能直接将现有 Mock dist 当正式包。

现有测试自行创建内存服务，不等价于真实 backend 合同测试。真实接口联调应覆盖持久化、权限、并发、跨日、幂等、文件及筛选导出，不只验证页面打开。

## 建议技术按这个顺序开发与验收

1. **先冻结规则：** 方案生效/疗程、分组快照、患者状态、退出范围、问卷轮次和权限。将 B01—B09、B16 转成明确任务。
2. **先打通一条真实链路：** 项目→分组→建档→个人方案→首次发药→患者确认→服药记录→后台统计；验证持久化与异常回滚。
3. **再接三条联动链路：** 问卷任务→该轮答卷→导出；检查任务→报告→核对/补充→任务状态；事件上报→人工跟进→待办和导出。
4. **最后统一界面与环境：** 列表核心列、日期语义、只读跳转、权限提示、加载失败、真实上传/OCR/提醒及部署配置。
5. **冻结开发基线：** 接口合同与文档和代码一致，测试更新后全绿，关键真实链路实际验收，记录明确未交付范围。
